# Phase 6, 6.1 & 6.2: Validated Fill-Packet API, Security Hardening & Lifecycle

## 1. Overview and Architecture

Phase 6 introduced a minimal, authenticated local API that delivers a validated, service-specific field packet from a currently reviewed case, accompanied by a Flask "Ready to fill" screen with per-field Copy buttons. Phase 6.1 hardened operator-confirmation enforcement, origin restrictions, event payload schemas, and token file permissions. Phase 6.2 validated review confirmation semantics, evidence lifecycle freshness across all mutation paths, and local session secret persistence.

This API acts as the data interface that a future Chrome Manifest V3 extension (Phase 7) will consume. No Chrome extension, browser content scripts, DOM manipulation, or automated form filling are implemented in Phase 6, 6.1, or 6.2.

### Architectural Principles

1. **Local-First & Offline**: Flask binds strictly to `127.0.0.1`. No external cloud services, remote telemetry, or OAuth providers.
2. **Strict Review Enforcement**: Fill packets are only emitted for cases that are currently in `status == 'reviewed'` with valid review timestamps and review versions.
3. **Operator-Confirmed Values Only**: The packet contains only operator-confirmed values approved during the review step. Raw OCR candidates without operator confirmation, document paths, confidence scores, and bounding boxes are strictly excluded.
4. **Conflict Freshness & Lifecycle Invalidation**: Any new evidence (agreeing or conflicting), manual document assignment, case merge, or unresolved conflict invalidates existing review metadata and blocks packet issuance (`409 Conflict`).
5. **No Blind Trust of Localhost**: API routes are protected by a cryptographically strong Bearer token stored outside git, validated using constant-time comparison, with cross-origin restrictions.

## 2. Operator-Confirmed Values vs. OCR Candidates

### Module: `app/services/fill_packet.py` and `app/services/review.py`

In FormFlow:
- **OCR Candidates**: Rows in `extracted_fields` generated by document parsing/OCR have `method` set to values such as `"text:labeled"`, `"ocr:labeled"`, etc., along with a `document_id`.
- **Operator-Confirmed Values**:
  - **Required fields (`full_name`, `dob`)**: When a case has `status == 'reviewed'` and valid `reviewed_at`, the populated value accepted by the operator during "Validate & Save" represents operator confirmation (whether matching an accepted OCR candidate without redundant DB rows or an explicit `method == 'manual'` edit). If the case is not reviewed, raw OCR candidates are never fill-eligible.
  - **Optional fields (`father_name`, `address`, `licence_no`)**: Confirmed when explicitly recorded via an operator edit or conflict pick (`method == 'manual'`). Unconfirmed OCR candidates on optional fields are never exposed as fill-eligible (`"Value not confirmed by operator"`).
  - **Application number (`application_no`)**: Persisted strictly at the case level in `cases.appl_number` (never duplicated into candidate rows in `extracted_fields`). If `cases.appl_number` is empty, it remains unavailable (`"Value not available"`).
  - **Deliberately blank fields**: Optional fields left blank or deliberately cleared by the operator are emitted with `value: null`, `eligible_to_fill: false`, and `reason: "Value not available"`. Values are **never fabricated**.

## 3. Fill-Packet Service Contract & Workflow Allowlists

The service `build_fill_packet(conn, case_id, workflow="dl_application")` constructs the packet.

### Workflow Configuration & Allowlists

Workflows define which semantic fields are eligible for a given service desk action.
The initial supported workflow is:
- **`dl_application`** (Driving Licence Application):
  - Fields: `full_name`, `father_name`, `dob`, `address`, `licence_no`, `application_no`

*Limitation*: Phase 6 defines only semantic keys and eligibility rules. Specific Sarathi portal form field IDs, DOM selectors, or state-specific portal variants are intentionally deferred to Phase 7.

### Field Eligibility Rules

A field entry has `eligible_to_fill: true` only when:
1. The case has `status == 'reviewed'` with valid `reviewed_at`.
2. The field belongs to the selected workflow allowlist.
3. An operator-confirmed value is present (for `application_no`: `cases.appl_number`; for required fields: validated value on reviewed case; for optional fields: recorded `method == 'manual'` row).
4. No unresolved conflicts or fresh contradictory candidates block the field.

## 4. Local API Authentication & Security Design

### Module: `app/services/api_auth.py` and `app/routes/api.py`

1. **Token Generation & Stability**:
   - `api_auth.ensure_token()` generates a 256-bit cryptographically secure token using `secrets.token_hex(32)`.
   - The token is stored in `data/.api_token` (gitignored).
   - If a valid token file already exists, it is **never overwritten** during ordinary application startup.
2. **File Permissions by Platform**:
   - **POSIX (Linux/macOS)**: Enforces owner-only permissions `0o600` (`-rw-------`) during creation and via `os.chmod`.
   - **Windows**: Standard Python `os.chmod` only modifies the read-only attribute on Windows and does not manage NTFS DACLs. The file is placed within the user's private application data directory (`data/`), inheriting local user profile access control.
3. **Token Recovery Limitations**:
   - There is no web-based token recovery or reset endpoint.
   - To recover or inspect the token, the machine owner reads `data/.api_token` directly.
   - To rotate or regenerate the token, the operator deletes `data/.api_token` and restarts the application.
4. **Header Authentication**: Requests must provide `Authorization: Bearer <token>`.
5. **Constant-Time Comparison**: Tokens are compared using `hmac.compare_digest()` to prevent timing side-channels.
6. **Hardened Origin Policy**:
   - Rejects non-localhost origins (e.g. `https://evil.com` or `http://127.0.0.1.attacker.com`).
   - Rejects unexpected localhost ports (e.g. `http://localhost:8080`); only the configured application port is accepted.
   - Rejects `Origin: null` (sandboxed iframes, `data:` URIs, or `file://` URLs).
   - Rejects malformed origins.
   - **Missing Origin Header**: Explicitly permitted for local non-browser clients (PowerShell `Invoke-RestMethod`, `curl`, CLI tools, and automated pytest suites) as well as same-origin browser GET requests that omit the header. These requests remain strictly protected by mandatory Bearer token authentication.
7. **Session Secret Configuration (`app/config.py`)**:
   - For local desktop and development runs without an explicit environment override, FormFlow generates a persistent 256-bit random session secret stored in `data/.session_secret` (gitignored, 0o600 on POSIX).
   - This prevents shared static defaults across installations while keeping local operator cookies stable across server restarts.
   - For any production or multi-user deployment, an explicit high-entropy secret **must** be provided via the `FORMFLOW_SECRET_KEY` environment variable (or `secret_key` in `config.local.json`). An unmanaged default is never suitable for production deployment.

## 5. API Endpoints and Event Schema

### 1. `GET /api/cases`
Returns a minimal list of selectable cases. Excludes OCR text, customer addresses, and applicant field values.

**Response (200 OK)**:
```json
{
  "cases": [
    {
      "case_id": "CASE-20261016-001",
      "status": "reviewed",
      "reviewed": true
    }
  ]
}
```

### 2. `GET /api/cases/<case_id>/fill-packet?workflow=dl_application`
Returns the validated fill packet for the case.

**Error Status Codes**:
- `401 Unauthorized`: Missing or invalid Bearer token.
- `403 Forbidden`: Disallowed Origin header.
- `404 Not Found`: Case does not exist.
- `400 Bad Request`: Unknown or invalid workflow.
- `409 Conflict`: Case is not reviewed (`case_not_reviewed`), missing review metadata (`review_metadata_missing`), or has unresolved conflicts (`unresolved_conflicts`).

### 3. `POST /api/cases/<case_id>/events`
Records operator or extension events to `case_events`.

**Payload Schema**:
- `event_type` (required, string): Must be one of `{"copy_attempt", "fill_attempt", "restore_attempt"}`.
- `review_version` (required, integer): Must be a strictly positive integer (> 0). Python booleans (`True`/`False`) are explicitly rejected.
- `field_key` (string):
  - Required for `copy_attempt` (must be in `REVIEW_FIELDS`).
  - Optional for `fill_attempt` and `restore_attempt` (if provided, must be in `REVIEW_FIELDS`).
- `detail` (optional, string): Max 100 characters.
- Any unexpected properties outside `{"event_type", "review_version", "field_key", "detail"}` are rejected (`400 Bad Request`).

**Sanitized Event Storage**:
Recorded in `case_events` as:
```json
{
  "event_type": "copy_attempt",
  "review_version": 1,
  "field_key": "full_name"
}
```
No applicant values, tokens, or unvetted strings are recorded.

## 6. Review Lifecycle & Freshness Protection

Phase 5.1.1 introduced `conflict_acks` to track acknowledged evidence. Phase 6 and 6.1 tightened the review lifecycle:

- In `app/services/match.py`, whenever candidate fields attach to a case that is currently `reviewed`, `touch_case_for_edit()` is invoked regardless of whether a conflict is detected.
- This immediately resets `status = 'needs_attention'`, clears `reviewed_at = NULL`, increments `review_version = review_version + 1`, and logs an `edit_after_review` event.
- New evidence always requires operator re-review.
- Stale review versions in event reporting or packet issuance are rejected (`409 Conflict`).

## 7. Ready to Fill View (Copy Fallback)

### Route: `GET /cases/<case_id>/fill-ready`
- Accessible via the **Ready to Fill** button on the Case Detail page for reviewed cases.
- Displays a clean table of workflow fields with operator-confirmed values and "Ready" badges.
- Per-field **Copy** button uses the modern asynchronous Clipboard API (`navigator.clipboard.writeText`), with an automatic hidden-textarea fallback for older browser environments.
- Missing or unconfirmed fields display "Unavailable" or "Value not confirmed by operator" and disable the Copy action.
- Copy actions target only the displayed value for that specific field.
- Clipboard failures report a clear, non-leaking message: `"Clipboard unavailable — select and copy manually."`
- Does not expose tokens, raw OCR text, or bounding box coordinates.
- Contains no applicant data in query parameters or persistent browser storage.

## 9. Manual Verification Checklist

When running the application locally:
1. Start the server: `run.bat` or `python run.py`.
2. Navigate to `http://127.0.0.1:5000/cases`.
3. Pick a case, complete review, and click "Validate & Save".
4. On the Case Detail page, click the new **Ready to Fill** button.
5. Click **Copy** next to "Full name" or "Address"; verify that the text copies to your clipboard.
6. Test API authentication via PowerShell:
   ```powershell
   $token = Get-Content data\.api_token
   Invoke-RestMethod -Uri "http://127.0.0.1:5000/api/cases" -Headers @{ Authorization = "Bearer $token" }
   ```
7. Verify cross-origin defense:
   ```powershell
   # Disallowed external origin returns 403 Forbidden
   try {
       Invoke-RestMethod -Uri "http://127.0.0.1:5000/api/cases" -Headers @{ Authorization = "Bearer $token"; Origin = "https://evil.com" }
   } catch {
       $_.Exception.Response.StatusCode # 403
   }
   ```
